# Writing an NX Orbit source plugin

A **source plugin** turns one place you already have an account into a stream of
Orbit records about the friends *you already have there*. This doc is the
contract you build against. It is enforced — the core rejects batches that break
it (§3 of [`SPEC.md`](../SPEC.md)), and PRs that break the charter (§0) are
declined regardless of whether the code runs.

If you read one thing: **a plugin may only emit what your own logged-in account
already shows you about your own friends. Nothing more is welcome here.** This is
the whole reason Orbit exists instead of the thing it refuses to be.

---

## The five rules (a plugin that breaks one is not merged)

1. **Friends-only, first-person.** Enumerate *your* friends / mutuals / followed
   accounts, logged in as *yourself*. Never crawl strangers, search, "expand" a
   graph, or touch anyone who hasn't opted into a relationship with you.
2. **Surface-only.** Emit only what the app already renders to you. No hidden
   endpoints, no DMs/message bodies, no de-anonymization, no scraping fields the
   UI hides. If you had to reverse a private API to get it, drop it.
3. **Observations, not conclusions.** Report events with timestamps. Never emit a
   score, a guess, a sentiment, a predicted schedule, or an inferred anything.
   The `kind` enum has no room for it by design — don't route inference through
   `meta`.
4. **Local delivery only.** Hand data to the core over the loopback ingest
   endpoint or as an in-process reader. A plugin must not phone home, and must
   not accept data *about* the operator's friends *from* anywhere remote.
5. **Verbatim + attributed.** Text (status, bio) is passed through exactly as the
   person wrote it. Every record carries your plugin's name and real timestamps
   so the operator can audit and purge your source.

A friend should be able to read every record your plugin emitted about them and
feel *seen*, not *surveilled*. That's the test.

## Two ways to deliver

### A. In-process reader — when the data is already a local file

Best when the source is a database/log already on disk (VRCX, a chat client's
local store). You get a JS module in `src/main/plugins/<name>.js` that the core
runs on a timer. Export:

```js
export const meta = { name: "vrcx", version: "1.0.0", source: "vrcx" };

// Called on a schedule. Return a Batch (SPEC §3). Throw to report failure.
// Re-scan the whole source each run — ingest dedups, so idempotency is free.
export async function collect(ctx) {
  // ctx.log(msg), ctx.paths (config dirs), ctx.settings
  return {
    plugin: "vrcx", version: "1.0.0", emittedAt: Date.now(),
    persons: [ /* Person[] */ ],
    observations: [ /* Observation[] */ ],
  };
}
```

Rules: open external files **read-only**, wrap every query in try/catch (the
source app may hold a lock), never write to the source. See
[`src/main/plugins/vrcx.js`](../src/main/plugins/vrcx.js) — the reference reader.

### B. External emitter — when the data lives in another app or needs its own auth

Best when the source is a running app you're inside (a Vencord userplugin in
Discord) or a service needing its own login (Twitter/X). Your plugin runs in its
own process and **POSTs a batch** to the loopback ingest endpoint.

```
POST http://127.0.0.1:8477/ingest
Authorization: Bearer <token from ~/.config/nx-orbit/ingest.token>
Content-Type: application/json

{ "plugin":"twitter-orbit", "version":"1.0.0", "emittedAt":1690000000000,
  "persons":[…], "observations":[…] }

→ 200 { "accepted": {persons:N, observations:M} }
→ 422 { "rejected": [{ index, field, reason }, …] }   // whole batch refused
```

- The endpoint binds **127.0.0.1 only**. It will never be reachable off-box.
- `GET /health → 200 {ok:true}` to check the core is up before emitting.
- The token is generated by the core on first run and shown in Settings →
  Sources. Rotating it there invalidates old emitters until reconfigured.

Building a Discord source specifically? [`docs/VENCORD_SOURCE.md`](VENCORD_SOURCE.md)
is a full walkthrough — the stores to read, the Discord→Orbit record mapping, the
delivery mechanics, and a ~60-line skeleton.

See [`plugins/vencord-orbit-bridge/`](../plugins/vencord-orbit-bridge/) (runs
inside Discord, reads your friends list + presence you can already see) and
[`plugins/twitter-orbit/`](../plugins/twitter-orbit/) (a small Node CLI you run
while logged in, reads accounts *you follow* from your own timeline).

## Record shapes (copy these — the core rejects anything else)

A **Person** (upsert; `source` + `sourceId` identify them):

```js
{ source:"discord", sourceId:"228534106599948289", handle:"friend#0",
  displayName:"Friend", avatarUrl:"https://cdn.discordapp.com/…",
  birthday:null, pronouns:"they/them", bio:null, note:null }
```

An **Observation** (`kind` MUST be in the enum: presence, status, location, bio,
nick, avatar, friend):

```js
// went online
{ source:"discord", sourceId:"2285…", kind:"presence", status:"online", ts:1690000000000 }
// set a custom status that says they're away
{ source:"discord", sourceId:"2285…", kind:"status", text:"🏖 back on the 20th", ts:1690000000000 }
// changed their display name
{ source:"discord", sourceId:"2285…", kind:"nick", text:"NewName", meta:{previous:"OldName"}, ts:1690000000000 }
```

Omit any optional field you don't have — **never** send an empty placeholder or a
made-up value. Timestamps are epoch ms of when the thing *happened*, not when you
scraped it.

### The one special person: `self`

If — and only if — your source can see **the operator's own** online history, emit
the reserved person `{source:"self", sourceId:"me", displayName:"(you)"}` plus
`presence` observations about it. This is the "me" axis the overlap heatmap needs;
without it, "hours we were *both* online" isn't computable. The VRCX reader does
this from your own gamelog.

Rules: `sourceId` MUST be exactly `"me"` (validation rejects anything else), it
describes **only the operator**, and it never appears in the friends roster.
Emitting a `self` record about someone who isn't the operator is a charter
violation, not a bug.

It is a **presence anchor, not a display identity.** Every source that can see
the operator emits it, so ingest stores only `(source, sourceId)` and drops
`handle`, `displayName`, `avatarUrl` and the rest — otherwise the operator's own
row would flap between their Mastodon handle, their Last.fm name and their
Matrix ID depending on which plugin ran last. Sending those fields is not an
error; they're just ignored. Don't work around it.

## Checklist before you open a PR

- [ ] Every person I emit is a mutual/friend/followed account of the operator.
- [ ] Every field came from what the app already showed the logged-in operator.
- [ ] No `kind` outside the enum; no inference smuggled through `meta`.
- [ ] I re-scan fully each run and rely on dedup (no fragile cursors).
- [ ] External source read-only; I never write to or alter the source app.
- [ ] `README.md` in my plugin folder states exactly what it reads and why each
      field is first-person-visible.
- [ ] A friend reading their own emitted records would feel waved at, not watched.
